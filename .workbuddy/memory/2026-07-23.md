## 第五次迭代：真·Kotlin 编译错误定位+修复 (v1.10.228, commit d949c3d)
- 用户第五次贴截图（00:21），加强的 grep 起效了，抓到了真错误：
  ```
  e: MainActivity.kt:149:13 'onReceivedError' overrides nothing
  e: MainActivity.kt:160:13 'onReceivedHttpError' overrides nothing
  ```
- **根因**：androidx.webkit:1.10.0 的 `WebViewClientCompat.onReceivedError(view, request, error)` 三个参数都是 **non-null**，但 MainActivity.kt 把它们声明成 `WebView?`、`WebResourceRequest?`、`WebResourceError?` 全 nullable。Kotlin null-safety 让 override 兼容性失败。
- 修复：去掉 `?`，让参数 non-null（保留 callback 功能，只改 nullability，不影响逻辑）。
- commit `d949c3d` push 成功 `4124e69..d949c3d main -> main`。CI 应能成功出 `chilly-phone-native-1.10.228.apk`。
- **教训**：Kotlin 编译错误格式 `e: <path>.kt:<line>:<col>: error: <msg>` 必须能 grep 到；之前漏了 `e: ` 前缀导致 3 轮瞎猜（npm ci / system gradle / wrapper gradle 全部猜错）。

## 第六次迭代：真根因=WebViewClientCompat 的 final 方法 (v1.10.229, commit a14a418)
- 用户第六次贴截图(00:23),grep 抓到了更具体的错误：
  ```
  e: MainActivity.kt:149:13 'onReceivedError' in 'WebViewClientCompat' is final and cannot be overridden
  e: MainActivity.kt:160:13 'onReceivedHttpError' in 'WebViewClientCompat' is final and cannot be overridden
  ```
- **真根因（推翻上次的判断）**：androidx.webkit:1.10+ 的 `WebViewClientCompat` 把 `onReceivedError` 和 `onReceivedHttpError` 标成 `final`（为内部 platform version dispatch 锁住向后兼容行为），子类**完全不能 override**。v1.10.228 我以为错在 nullability，其实错在用了 `WebViewClientCompat` 这个父类。
- 修复：
  1. `import androidx.webkit.WebViewClientCompat` → `import android.webkit.WebViewClient`（标准版这两个方法可正常 override）
  2. `object : WebViewClientCompat()` → `object : WebViewClient()`
  3. `onPageStarted(view: WebView?, ...)` / `onPageFinished(view: WebView?, ...)` 的 `WebView?` 改成 `WebView`（标准 WebViewClient 用 non-null）
- commit `a14a418` push 成功 `d949c3d..a14a418 main -> main`。CI 应能编译通过。
- **教训**：Kotlin 编译错误从"overrides nothing"升级到"is final and cannot be overridden"时，父类本身可能是错的——不是参数 nullability 的问题。下次看到 "is final" 立刻换父类，别再瞎调 nullability。
- 仍然可用的修复：`shouldInterceptRequest` 签名在两个父类里都是 `(WebView, WebResourceRequest) -> WebResourceResponse?`,`WebViewAssetLoader.shouldInterceptRequest(url)` 独立于父类,不需要 WebViewClientCompat。

## 第七次迭代：情侣空间相册生图"过一天就没了" (v1.10.230, commit 6fc5bea)
- 用户问：火山引擎生图没永久留存，情侣空间相册图片过一天就没了。
- **根因**：火山方舟文生图 API(`ark.cn-beijing.volces.com/api/v3/images/generations`)返回的 `data.data[0].url` 是**带签名的临时图片链接，有效期约 24 小时**（官方文档："url 形式的图片地址是有效期限制的"）。代码本意用 `_persistImageUrl(url)` 把图 fetch 成 base64 永久存，但 `fetch` 跨域图经常因 CORS / 30s 超时失败，fallback `if (!resp.ok) return url` 把"24h 临时 URL"直接存进了 `loveSpaceStore` 的相册 → 第二天链接过期，图没了。
- 存储层本身没问题：`addToAlbum` → localforage IndexedDB(`love_space` 库 `all_spaces_v2` key) 是持久化的；问题出在存的内容是"临时 URL 而非图片本身"。
- **修复**(src/utils/aiService.js)：
  1. 火山请求 `response_format: 'url'` → `'b64_json'`，让方舟直接返回 base64，彻底绕开"临时 URL + fetch 跨域失败"链路。
  2. 裸 base64(无 `data:` 前缀)补全 `data:image/png;base64,` 前缀，否则 `<img src>` 显示不出来。
  3. `_persistImageUrl` 原本遇到 `data:` 直接 return（不压缩）；改为 `data:` 也走 compressImage(800×800 q0.7)，控制 IndexedDB 占用。
- commit `6fc5bea` push 成功 `a14a418..6fc5bea main -> main`。CI 应重建 PWA + 原生 APK 1.10.230。
- **说明给用户**：① fix 只影响"新生成"的图；② 之前已经存成临时 URL 的老图无法恢复（链接已过期、没存原始数据）；③ 这是网页/PWA 功能，原生 APP(WebView 加载 dist) 也要重新打包 APK 才能拿到修复（build-native-apk.yml 会在 push 时自动 npm run build → 复制 dist → assembleRelease）。
- **经验**：任何第三方图床/生图 API 返回的 URL 都必须假设会过期；存储图片永远存 base64/blob 本身，不要存外链。这是移动端离线优先架构的基本原则。

## 第八次迭代：v1.10.230 release 误装 2.42MB 网页壳 (TWA vs Native release 区分)
- 用户反馈：截图里 `https://github.com/chilly520/qiaqiao-phone/releases/tag/v1.10.230` 只有 `chilly-phone-1.10.230.apk` (2.42MB)，没 native。
- **真因**：仓库 `.github/workflows/` 有 **两个** APK workflow，都在 `push: branches: [main]` 触发，但产物名/tag/release title 完全不同：
  - `build-apk.yml` (TWA 网页壳, bubblewrap) → `chilly-phone-<ver>.apk`，tag `v<ver>`，title `Chilly Phone <ver>`，~2MB
  - `build-native-apk.yml` (真原生, Kotlin WebView + assets/dist) → `chilly-phone-native-<ver>.apk`，tag `v<ver>-native`，title `Chilly Phone Native <ver>`，~49MB
- 用户看到 release 列表的 "Latest" tag 是 `v1.10.230`，就下了网页壳，没注意到 native 那个 `v1.10.230-native` 应该独立发。
- **诊断**：native workflow 大概率 gradle build 又挂了，所以 `v1.10.230-native` release 没出。需要用户去 Actions 拿日志。
- **教训**：CI 设计上 native 和 TWA 应该是**两个独立 release**，但 push 会同时触发；TWA 快(2~3 分钟)先出，native 慢(5~10 分钟)后出。两者 tag 必须明确区分（带 `-native` 后缀）避免混淆。下次发版要在 release 列表里确认两个 tag 都出来了再告诉用户。
- **架构补充（关键）**：PWA 网页壳(android-app/) 是 bubblewrap 把 dist 当 PWA 远程加载（GitHub Pages），本地无 assets；和 native android-native/（WebView 读本地 assets/dist）是**两套不同的安卓项目**。PWA 壳可以装但加载的是网络 PWA，不会自动同步到 native 改了 dist 后的代码——除非 GitHub Pages deploy.yml 也跑了。
