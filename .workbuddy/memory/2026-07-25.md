## ⚠️ 仓库 .git 损坏 + 抢救（19:06-19:20，重要经验）

**现象**：一次本地 commit（husky hook Windows 路径 bug 退出 1）后，所有 git 命令突然报 "not a git repository"，连 `git -C`/`--git-dir` 都失败。

**根因**：那次失败 commit 的 hook 内有 "Backing up original state..." 操作，把 `.git/refs/` 整个目录删了，并弄丢一个 object（c90b128）。`.git` 数据（packed-refs/objects/HEAD）都还在，但 git 的 `is_git_directory` 要求 `refs/` 存在，否则判非仓库。

**安全恢复（未丢任何工作区改动）**：
1. `mkdir -p .git/refs/heads .git/refs/tags .git/refs/remotes/origin`（纯新增空目录，git 即从 packed-refs 重认仓库）
2. `git fetch origin`（补全缺失 objects + 拉回完整远端历史/所有 tag）
3. `git read-tree origin/main`（index 重置到完整链 092c878 的 tree，绕开损坏 object）
4. `git reset --soft origin/main`（HEAD=092c878=origin/main，保留工作区+index）

## 用户搜索快捷键修复（1.10.239，本地 commit + push）

**用户反馈**：手打 `[[SEARCH:深圳 最新台风 2026年7月]]` 期望触发搜索，AI 却返回空内容（截图 `prompt_tokens:150330, completion_tokens:28, message.content` 空）。

**根因**：用户输入 `[[SEARCH:...]]`（双中括号）不被任何协议识别——
① 单中括号 `[搜索:/[SEARCH:/[查找:` 协议（chatStore.js 5145）只认单括号；
② `[SEARCH]...[/SEARCH]`（aiService.js）是记忆检索 RAG-lite 协议（不同格式）；
③ 双中括号 `[[...]]` 代码完全不认 → 走普通聊天路径 → AI 面对含 status 块的异常输入吐空。
**150k token 不是问题**（用户纠正："平时聊天 150k 正常输出，我的模型支持 100m"）。

**修复**（3 文件 + 版本 bump）：
- `src/stores/chatStore.js`：新增 `runUserSearch(chatId, keyword, mode)`，复用 `/v2/search/bing` 逻辑（显示 search 气泡 role:user → 注入 hidden 系统消息 → `sendMessageToAI({_isToolContinuation:true})`），并暴露到 store return。
- `src/views/WeChat/ChatWindow.vue` 与 `OfflineModeChatWindow.vue` 的 `handleSendMessage`：开头检测 `^\[\[?\s*(?:搜索|SEARCH|查找)[:：]\s*(.+?)\s*\]+$`（兼容单/双中括号 + 中英关键词），命中则拦截并 `runUserSearch` 而非走普通聊天。
- 版本 bump 1.10.238→1.10.239（src/version.json，build 自动 sync public/）。

**验证**：esbuild 构建通过；node 单测正则 `[[SEARCH:...]]`/`[搜索:...]`/`[查找:...]` 均正确提取关键词，普通消息与带尾随文本消息不误命中。
